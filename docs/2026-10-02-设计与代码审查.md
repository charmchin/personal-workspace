## 1. 优先问题

### P1：恢复中断后，启动无法识别恢复前数据库

**修复状态：已在 0.1.2 实现（2026-10-02，第一项修复）。** 新流程同目录原子替换并同步文件和父目录；解锁后验证并处理新旧恢复遗留文件，禁止中断状态重新初始化或生成密钥。有效主库优先，必要时回滚已验证旧库；无法验证时保留文件并报错。新增独立子进程在四个替换节点直接退出的重启测试，以及旧版缺主库、错误口令/密钥、损坏候选、路径链接、保留 WAL、重新打开失败回滚等隔离测试。下文保留原审查证据；其他问题仍待后续指令处理。

本项验证：Rust 44 项通过，前端 11 项通过；格式检查、Clippy 和生产构建通过。Rust 默认列表中另有两项忽略：性能测试本项未重跑；中断测试子进程入口由父测试显式调用了四次，并非跳过中断检查。所有恢复、删除与错误注入均使用临时测试库，未操作用户真实数据库、密钥或备份。桌面安装与真实启动需在用户保存并退出旧版后进行，避免运行中替换和多实例。

位置：[备份替换逻辑](../src-tauri/src/backup.rs)、[初始化与状态判断](../src-tauri/src/database.rs)。关键位置为 `backup.rs:245–283` 和 `database.rs:87–91`。

恢复先把当前库改名为 `database-before-restore.sqlite3.tmp`，再把新库改名为 `workbench.sqlite3`。如果两次改名之间进程被强制终止，主数据库路径暂时不存在。启动逻辑没有恢复状态检查，只凭主文件存在与否判断是否初始化。

隔离测试模拟了这个文件状态：旧库仍在临时路径，重新创建 AppState 后却返回 `initialized=false`。这是已复现的恢复流程缺口；没有声称用户真实数据已经丢失。现有恢复前快照仍可成为补救来源，但应用没有自动接续或回滚入口。

建议：启动时识别未完成恢复；校验旧库与候选库后恢复一致状态，禁止当作全新工作台初始化；补充文件及父目录持久化，并覆盖每一步中断后的重启测试。

### P1：系统锁屏立即锁定没有原生后端保障

**修复状态：已在 0.1.3 实现（2026-10-02，第二项修复）。** 新增独立会话策略、250ms 后端闲置监视、原生分布式和工作区事件监听、命令进入/返回时的授权检查及认证代号校验。锁定通知不等待数据库操作；先撤销授权，已开始的写入安全收尾后关闭连接。主事件循环不再执行同步数据库/备份命令。页面清理口令、弹窗和业务内容，并补充状态核对及旧响应抑制。恢复备份后同步更新锁定期限；行情循环跨会话失效后停止后续请求/写入，但重定向策略和立即取消在途 HTTP 仍属于待处理的联网问题。

验证包含后台期限、过期活动不能复活、忙碌数据库锁不阻挡撤销、认证中断、唤醒不自动解锁、独立屏幕锁不能被唤醒状态误清除、返回敏感查询结果前复核、前端 DOM 清理与旧认证响应抑制。原生主线程进程使用私有测试通知名称验证真实通知中心注册、分布式回调和监听移除；未触发用户 Mac 真实锁屏。实际锁屏/睡眠/唤醒的交互验收仍需用户配合，不将模拟测试写成实机验收通过；通知可靠性与在途操作边界见开发说明。下文保留原审查证据。

本轮结果：54 项 Rust 单元测试、17 项前端测试通过，另通过主线程原生通知冒烟进程；格式、Clippy、生产构建、arm64 和本地临时签名验证通过。两项默认忽略说明沿用上一轮：性能本轮未重跑，恢复中断子进程由父测试实际运行。0.1.3 已替换安装到 `/Applications/个人工作台.app`，累计包含前两项修复；升级前 0.1.1 应用保留在源码构建目录的 `个人工作台-0.1.1-升级前.zip`，ZIP 完整性检查通过。没有使用真实业务数据执行恢复、改口令或故障注入。

安装后已从标准应用路径启动，确认新版本进程持续运行且安装包签名有效；此为启动存活检查，不等同于已人工检查全部页面、完成系统认证或真实锁屏/唤醒验收。

位置：[App.tsx](../src/App.tsx) 第 136–163 行、[桌面入口](../src-tauri/src/lib.rs)。

当前自动锁完全由前端定时器与 `document.visibilitychange` 驱动，页面隐藏后再延迟一秒调用后端。Rust 没有订阅 macOS 锁屏事件，也没有独立的闲置期限检查。

静态确认：实现无法独立保证 README 和设置页所称的“系统锁屏时始终锁定”。本次未操作真实系统锁屏，不能据此断言每次锁屏都会失败。WebView 挂起或没有发送可见性事件时，后端连接缺少主动关闭机制。

建议：macOS 原生锁屏通知触发 Rust 锁定；闲置期限由后端执行；同时通知前端清空页面缓存。验收应包含锁屏、唤醒、最小化和正在执行慢任务的情形。

### P2：日程时间存储、编辑和 ICS 导出不一致

位置：[日程页](../src/pages/SchedulePage.tsx) 第 118 行、[ICS 转换](../src-tauri/src/commands.rs) 第 927 行、[日程保存](../src-tauri/src/repository.rs) 第 317 行。

- 测试复现：界面创建的 `2026-10-02T09:00` 被原样保存；导出产生 `DTSTART:2026-10-02T09:00`，不符合 ICS 日期时间编码。应按上海时区解释，再输出例如 `20261002T010000Z`。[RFC 5545 日期时间格式](https://datatracker.ietf.org/doc/html/rfc5545#section-3.3.5)
- 静态确认：编辑框对带 UTC 时区的时间直接 `.slice(0, 16)`。例如 `01:00Z` 在上海应显示 `09:00`，编辑框却显示 `01:00`；保存后可能把事件提前八小时。
- 测试复现：导入 `TZID=America/New_York` 会丢弃 TZID，将当地 09:00 存为上海 09:00；`RRULE` 中的 `COUNT`、`UNTIL`、`BYDAY`、`INTERVAL` 也没有完整解析，可能变成无限的简单重复。
- 静态确认：月历只按开始日匹配，多日事件未覆盖后续日期；首页下一次重复的日期计算使用字符串中的原始日期，可能与转换后本地日期不一致。

建议：时间点统一存 UTC，显示及编辑显式转换上海时区；全天事件独立存日期，保留结束日期语义；对不支持的 ICS 规则明确报告，不静默改写。增加“界面创建—导出—再导入—编辑”的真正往返测试。

导入和导出按钮目前绑定的操作正确，没有发现两者接反；问题在日期转换和文件内容。

| 分红 10、手续费 1、税费 2 | 测试复现：已实现收益为 10，按当前表单字段语义应为 7 | 统一分红的净额计算与字段定义 |

### P2：删除交易没有验证剩余交易序列

位置：[删除接口](../src-tauri/src/repository.rs) 第 1144–1169 行。

测试复现：先买入 10 份，再卖出 5 份，调用后端删除买入记录成功；随后投资汇总和首页都返回 `INSUFFICIENT_POSITION`。新增交易已有事务验证，删除交易却没有同等验证。

当前投资页面没有删除按钮，因此不是现有页面每次操作都会触发；但后端已经开放该删除类型。

建议：交易删除和修改都在事务内验证完整时间序列，失败则回滚；首页应允许投资摘要失败时其他模块正常加载。

### P2：备份验证尚未达到原方案的完整性标准

位置：[验证方法](../src-tauri/src/database.rs) 第 987–1034 行、[备份恢复](../src-tauri/src/backup.rs) 第 358 行。

测试复现：一个带有孤立外键的测试库仍能通过 `validate_connection`；把结构版本设为 999 也不会被拒绝。校验目前是 `quick_check`、版本至少为 1，以及所有业务表总记录数。清单没有逐表记录数。

这不足以保证跨模块关系和未来版本兼容性；SQLite 的结构完整性检查也不能替代独立外键检查。[SQLite PRAGMA 文档](https://www.sqlite.org/pragma.html#pragma_integrity_check)

建议：恢复前执行外键检查、支持版本上限检查、必需表与字段校验、逐表记录数核对以及投资序列验证。未解锁的现有工作台也缺少“用独立备份恢复”的灾难恢复入口，遗忘工作台口令时无法直接从界面使用已知密码的备份。

### P2：日快照不包含同一天后续写入

位置：[自动快照](../src-tauri/src/database.rs) 第 897–922 行。

快照仅在解锁时调用。同名文件存在后立即返回；同一天再次解锁不刷新当日快照。测试复现：第一次快照后新增项目，再次创建快照，新增项目不在快照内。长时间不锁定、不重启时也不会在跨日后自动创建新快照。

当前行为可理解为“每日首次解锁时的恢复点”，并非当天最新备份；应在设置页明确这个含义。

建议：保留首次快照策略时补充定时或写入后的最新恢复点，并显示快照实际时间与覆盖范围；执行备份时采用后台任务，避免长时间阻塞锁定。

### P2：多实例恢复缺少协调

位置：[桌面入口](../src-tauri/src/lib.rs)、[备份恢复](../src-tauri/src/backup.rs)。

未发现单实例插件或跨进程恢复锁。隔离测试打开两个连接到同一数据库，再执行快照恢复，返回 `database schema has changed`。该测试中原数据仍能读取且后续写入成功，未证实数据丢失。

建议：本机工作台启用单实例，重复启动聚焦已有窗口；恢复、密钥修改和迁移另外使用进程间排他锁，覆盖开发副本与安装副本同时启动的情况。

### P2：联网仅限定 HTTPS，未完整限定目标域名与取消时机

位置：[行情刷新](../src-tauri/src/commands.rs) 第 484–533 行。

静态确认：初始请求地址固定为 Tushare，但 Client 仅设置 `https_only(true)`，没有重定向域名策略；关闭联网开关后，已经开始的循环也没有取消或再次检查开关。

reqwest 默认允许自动重定向，因此“初始 URL 固定”不能证明所有后续请求仍在指定域名。这里是可达性风险分析，没有实测 Tushare 的实际重定向，也没有证实 Token 泄漏。[reqwest 重定向文档](https://docs.rs/reqwest/0.13.4/reqwest/redirect/index.html)

建议：禁用重定向或仅允许准确的 Tushare 域名；联网关闭、锁定或恢复开始时取消行情任务；在写入行情前核对解锁会话和配置状态。为行情响应设置大小上限。

## 2. 页面与交互优化

以下基于页面与 CSS 静态审查，不代表已做全部窗口尺寸的截图验收。

1. **隐藏条目缺少展开入口。** 日程单日最多展示 8 个事件、2 个任务，任务侧栏最多 14 项；“还有 N 项”不能点击。应提供当天完整清单及任务筛选/分页。
2. **搜索没有直达记录。** 命令面板选择结果仅切换页面，没有传递记录 ID 或打开编辑；后端搜索未包含日历事件，证券仅搜索名称，不能按代码检索。请求结果也缺少过期响应保护。应支持名称和代码、记录定位及取消旧查询。
3. **保存错误可能位于弹窗后面。** 多数页面把 ErrorBanner 放在页面顶层，表单保留在原生 modal 顶层，错误反馈因此处于背景。应把表单错误放入弹窗，并聚焦问题字段。
4. **创建表单缺少重复提交保护。** 日程、投资、成长、工作等页面的保存按钮没有保存中禁用；空 ID 每次由后端生成不同 UUID，重复点击可能产生两条记录。应增加提交状态，关键写操作可用幂等请求 ID。
5. **长列表一次性加载并渲染。** 工作页遍历全部日志；日历对每个日期重复扫描全部任务和事件。建议先提供日期范围查询、分页和长列表虚拟化，再按需增加缓存。
6. **日周视图更像加高后的月历格子。** 当前没有时间轴、全天区、重叠时间块的布局。可把月视图保持简洁，日周视图改成按时间排列的行动列表或时间轴。
7. **内容流程的“待复盘”缺少快捷推进归档。** `review` 状态隐藏推进按钮，虽然仍可用归档图标，应采用明确文字动作提高可发现性。

不建议仅依靠扩大卡片、增加留白来解决这些问题。优先补齐“看见记录—打开记录—修改成功—获得反馈”的操作流程，再统一模块标题、主次按钮和分组间距。

## 3. 依赖安全检查

### 实际 macOS 构建会使用的 TLS 依赖

`Cargo.lock` 第 3940 行锁定 `rustls 0.23.43`。`cargo tree --target aarch64-apple-darwin -i rustls` 确认链路为 `个人工作台 → reqwest 0.13.4 → rustls`。

命中 [RUSTSEC-2026-0285](https://rustsec.org/advisories/RUSTSEC-2026-0285.html)，公告发布日期为 2026-09-14，修复版本至少 0.23.45，评级为中等。问题是接受错误加密阶段的 TLS 1.3 握手消息；公告同时说明握手内容仍被认证，不能据此推断中间人可以任意篡改或完成握手。

建议在兼容范围内更新锁定版本并重新构建应用。该路径与启用联网行情有关，不等于离线数据库加密被攻破。

### 前端开发依赖

`npm audit` 返回两项中等告警，实际对应同一个 [Vitest / @vitest/mocker 公告](https://github.com/vitest-dev/vitest/security/advisories/GHSA-82fw-gwwq-j7x9)。当前版本为 3.2.7，修复版本至少 4.1.11；3.x 不再提供此修复。公告的攻击条件涉及开发服务器及 mock 插件，当前常规 `vitest run` 未证实满足该攻击条件。

`npm audit --omit=dev` 返回零告警。这项开发依赖问题不能直接写成已安装应用的任意文件读取漏洞。升级测试工具后需要适配并重新验证测试。

### Rust 锁文件全量扫描的其他结果

通过 OSV batch 查询 611 个注册表包，再核对本机目标依赖树：

- `glib 0.18.5` 命中 RUSTSEC-2024-0429，但不是当前 Apple Silicon 构建依赖。
- `rkyv 0.7.46` 命中 RUSTSEC-2026-0235，但当前目标启用的依赖树没有该包。
- `proc-macro-error 1.0.4` 命中停止维护告警，当前目标依赖树没有该包。
- 五个 `unic-* 0.9.0` 包存在停止维护告警，部分通过 Tauri 的 urlpattern 工具链实际引入，应随上游替换关注；停止维护告警不等同于已确认可利用漏洞。

锁文件命中不直接等于当前运行路径可利用，以上已区分。扫描也不构成对全部依赖和操作系统的安全证明。

## 4. 文档及可维护性

现有[安装与卸载文档](安装位置、运行文件与彻底卸载.md)仍把工程写成 `/path/to/personal-workspace`，实际已重命名为 `/path/to/personal-workspace`。按旧路径执行卸载会留下当前源码、node_modules 和构建产物。应更新路径，并在执行删除前检查实际目标，不把历史扫描结果当作长期事实。

前端通用 `call<T>` 仅验证响应，未按原方案统一验证请求；Rust Serde 提供结构解码，领域方法提供部分语义校验，但这与完整双端请求校验有差距。可先统一日期、金融值和表单错误，再按领域提供类型化命令。

建议按领域拆分超过千行的 commands/repository 模块，把页面表单从长 JSX 单行拆出。继续保留现有数据库与 Tauri 架构，不引入无必要的新框架。
